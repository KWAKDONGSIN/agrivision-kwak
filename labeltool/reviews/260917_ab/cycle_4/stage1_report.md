## 7. 3단계(총괄)가 판정할 것

1. **687 로 둘 것인가, 703 으로 갈 것인가.** 최대 독립 집합을 쓰면 **16장을 더 살립니다**(제외 314→298).
   대가는 «2차가 고른 대표를 존중한다» 는 규칙을 버리는 것이고, README·PDF·3차판정서·툴 `duplicates.json`·
   `status.json` 의 숫자를 전부 고쳐야 합니다. **제 판단으로는 그대로 두고 «탐욕이라 최적보다 16장 더 뺐다» 를
   문서에 적는 쪽이 비용이 훨씬 작습니다.** 다만 논문에 «중복을 제거해 687장» 이라고 쓸 거라면
   **이 숫자가 알고리즘 선택의 결과라는 사실은 반드시 적어야 합니다.**
2. **2차 보고서 102행의 「196쌍」을 고칠 것인가.** 실제는 **177쌍**이고 정의도 다릅니다(§5).
   232 라는 결론은 맞으므로 아래 사슬은 전부 무사합니다. 문장만 틀렸습니다.
3. **§6-1·2 의 스크립트 부재를 메울 것인가.** 제 `independent_repro.py`·`frameadj232_repro.py` 가
   원본을 바이트까지 재현하므로 그대로 `inspect/.../scripts/` 에 넣으면 됩니다.
   **제가 넣지 않은 이유는 이번 사이클 지시에 `inspect/` 수정 금지가 있기 때문입니다.**
4. **§6-13 의 flag 12장.** 중복으로 빠진 12장에 「라벨 안 된 사과 후보」 좌표가 있었는데 사라졌습니다.
   같은 그룹의 대표 사진에도 같은 사과가 찍혀 있을 가능성이 높지만 **확인은 안 했습니다.**
   2단계에 사진 대조를 맡기시길 권합니다.
5. **`cv2.setRNGSeed(0)` · `sorted(os.listdir())` 두 줄**(§6-8·9)은 지금 넣으면 앞으로 영원히 안전합니다.
   이번엔 운 좋게 전부 같았습니다.

## 9. 가정

1. **«재현» 의 기준을 «바이트 동일»로 잡았습니다.** 실제로 그럴 필요가 있었던 것은 PDF 하나뿐이고,
   그것도 다른 바이트는 생성시각 4글자였습니다.
2. **빌드 재현에서 이미지 6 GB 복사는 건너뛰었습니다**(지시대로). manifest·status·duplicates 는
   이미지 복사와 무관하게 계산되므로 비교에 영향이 없습니다. 실제 이미지 장수는 현행 폴더에서
   따로 세어 확인했습니다(사과 687·블루베리 1,124 = manifest 와 일치).
3. **툴 `data/` 의 «실행 전» 상태**는 `_status_backup_260917_r3.json`·`duplicates_round1.json`
   (스크립트가 직접 만든 백업)이라고 보고 스크래치에 복원했습니다.
4. **정렬 «무작위 10회» 는 seed 0~9 의 `random.shuffle`** 로 정의했습니다.
5. **§3 의 «보간법을 바꿨다면» 은 눈 판정을 그대로 둔 가정 계산**입니다. 실제로 LANCZOS 로 후보를 뽑았다면
   사람이 본 시트 자체가 달랐을 것이므로, 표의 숫자는 **상한이 아니라 방향**으로만 읽어야 합니다.
6. **`inspect/` 와 `datasets_reviewed_260917/` 를 한 글자도 고치지 않았습니다.** 고칠 것 제안은 §6·§7 에만 적었습니다.
7. **`작업기록.md` 는 손대지 않았습니다** — 이번 사이클 지시에 수정 금지가 명시돼 있어 **사이클 5 총괄 몫**으로 남깁니다.
