### C1. (확실 · 고침) 모서리를 반대편으로 끌어 뒤집으면 상자가 찌그러진다 — `app.js` resize

**원인.** `boxMouseMove` 의 resize 분기가 **상자 자신의 좌표를 매번 다시 읽어** 한쪽 모서리만 마우스 자리로
바꾸고 `norm()` 으로 정렬했습니다. 마우스가 반대 모서리를 지나가는 순간 `norm()` 이 좌표 순서를 바꿔 버려,
**«고정돼 있어야 할 반대 모서리» 가 배열에서 자리를 옮기고 그 값이 다음 이벤트에서 마우스 좌표로 덮어써집니다.**
그 결과 상자는 «직전 마우스 자리 ~ 현재 마우스 자리» 크기, 즉 **한 이벤트당 마우스 이동량만 한 크기로 붕괴**합니다.
마우스를 촘촘히(=천천히) 움직일수록 더 작아지고, 확대 상태에서는 0×0 이 됩니다.

고치기 전 코드(`app.js` 991–996, 백업본에 있음):

```js
const b = S.boxes[S.bsel];
let [x1, y1, x2, y2] = b.xyxy;                    // ← 상자에서 다시 읽는다
if (S.drag.corner.includes("n")) y1 = clampY(y); else y2 = clampY(y);
if (S.drag.corner.includes("w")) x1 = clampX(x); else x2 = clampX(x);
b.xyxy = norm(x1, y1, x2, y2).map(Math.round);    // ← 뒤집히면 고정점을 잃는다
```

**재현** (`node cycles/cycle_1/stage2/sim_resize.js`, `[100,100,300,300]` 의 se 손잡이를 (50,50) 까지 끌기.
제대로면 반대 모서리 nw(100,100) 가 고정돼 `[50,50,100,100]` 이어야 함):

```
   한 이벤트 50px 이동: 지금 [50,50,100,100] (크기 50x50)   ← 아주 거칠게 끌면 우연히 맞음
   한 이벤트 10px 이동: 지금 [50,50, 60, 60] (크기 10x10)
   한 이벤트  2px 이동: 지금 [50,50, 52, 52] (크기  2x2)
   한 이벤트  1px 이동: 지금 [50,50, 51, 51] (크기  1x1)   ← 200x200 상자가 1x1 로
(3) 뒤집고 나서 다시 원래 자리로 되돌리기
   지금    : [50,50,300,300]      ← 고정점이 영구히 망가져 원래 크기로 회복 안 됨
   고친 뒤 : [100,100,300,300]
```

1픽셀 단위 마우스 이동은 실제 사용에서 정상이므로(= mousemove 는 보통 1~2px 씩 옵니다),
이는 «사람이 모서리를 반대편으로 넘기면 상자가 사실상 사라진다» 는 뜻입니다. 게다가 그 상자는
크기가 2픽셀 미만이 되어 **저장할 때 서버가 조용히 버립니다**(C2 와 겹쳐 피해가 커짐).

**고침.** 손잡이를 잡는 순간 **반대 모서리를 «고정점»(`ax`,`ay`) 으로 붙잡아** `S.drag` 에 넣고, 이동 중에는
상자 좌표를 다시 읽지 않고 «고정점 + 지금 마우스 자리» 로 매번 새로 만듭니다(B1 고침과 같은 방식).

```js
// boxMouseDown — 손잡이를 잡을 때
const [hx1, hy1, hx2, hy2] = S.boxes[S.bsel].xyxy;
S.drag = { mode: "resize", corner: h,
           ax: h.includes("w") ? hx2 : hx1, ay: h.includes("n") ? hy2 : hy1 };
// boxMouseMove — 이동 중
S.boxes[S.bsel].xyxy = norm(S.drag.ax, S.drag.ay, clampX(x), clampY(y)).map(Math.round);
```

`/img` 는 `send_file(img_path(...))` 로 **원본 파일을 그대로** 내려주고 `/api/item` 의 `width/height` 는
같은 파일의 `Image.open().size` 이므로(`server.py:674-680`, `649-659`), **화면 좌표계와 저장 좌표계가
같은 원본 픽셀**입니다 — 축소 미리보기를 내려주는 식의 좌표 어긋남은 없습니다.

## ④ 1차 판정에 대한 반박

### R1. (반박) ②-4 「우리는 좌표가 `[0,W]` 로 묶여 있어 `중심±반폭` 이 절대 1.0 을 넘지 않습니다」 — **틀렸습니다**

1차는 검출 팀 파일이 331줄에서 1.0 을 5e-7 넘는 것을 지적하며 «우리는 그렇지 않다» 고 적었지만,
우리도 **똑같이 넘습니다.** 원인은 좌표 범위가 아니라 **중심과 너비를 각각 `%.6f` 로 따로 반올림**하는
것입니다(`boxes.py:156-158`). 경계에 붙은 상자에서 바로 반례가 나옵니다.

```
$ python3 -c "cx,bw=0.999199,0.001603; print(cx+bw/2)"
1.0000004999999998          ← 1.0 을 넘음
$ python3 -c "cx,bw=0.000801,0.001603; print(cx-bw/2)"
-5e-07                      ← 0 보다 작음
```

이 값은 `[1246,1662,1248,1664]`·`[0,0,2,2]` 처럼 **사진 변에 붙은 작은 상자를 저장하면 반드시** 나옵니다
(위 C3 표의 실제 내보내기 결과입니다). 실제 피해는 거의 없습니다 — 검출 팀 파일도 같은 성질이고
학습기가 잘라 씁니다. **고치지 않았습니다**: 자릿수를 늘리거나 좌표를 잘라내는 것은 팀 형식과의 합의
사항이고 사이클 4 주제입니다. 다만 1차 보고서의 저 문장은 **사실과 다르므로 최종 판정서에 그대로
옮기면 안 됩니다.**

### R2. (반박) ① 「좌표 변환 … 자체는 정확했다」 는 결론이 근거보다 넓습니다

1차는 `toImg`·휠 확대·«옮기기» 만 시험하고 **«크기 조절» 을 한 번도 시험하지 않은 채** 좌표 변환 전반을
정확하다고 결론냈습니다. 실제로는 그 안에 B1 보다 피해가 큰 버그(C1)가 있었습니다.
1차 ②-2 표의 「`[500,600,400,500]` 뒤집힘 → 정렬됨 통과」 는 **서버 `clean()` 의 뒤집힘 처리**일 뿐인데,
이것이 «뒤집힘은 확인됐다» 는 인상을 주어 화면 쪽 뒤집기 버그를 가렸습니다.
→ 사이클 2~5 에서 «어떤 조작을 시험했고 어떤 조작을 안 했는지» 를 표로 남길 것을 권합니다.

### R3. (보탬) ②-2 「`[10.4,20.6,60.5,70.5]` → `[10,21,60,70]` 통과 (파이썬 round)」 — 통과지만 규칙이 두 개입니다

서버는 파이썬 `round()`(0.5 는 짝수로), 화면은 `Math.round()`(0.5 는 올림)를 씁니다.

```
python round(60.5) = 60   |  JS Math.round(60.5) = 61
python round(12.5) = 12   |  JS Math.round(12.5) = 13
```

지금은 화면이 **항상 정수로 반올림해 보내므로**(`boxMouseUp`·move·resize 모두 `Math.round`) 이 차이에
닿지 않습니다. 하지만 «소수 좌표를 보내는 경로»(외부 도구·초벌 변형·나중의 API 사용자)가 생기면 화면과
서버가 1픽셀 다르게 반올림합니다. 실효 버그가 아니므로 **안 고쳤습니다** — 1차 D5 와 같은 «일관성» 칸에
넣어 두면 충분합니다.
