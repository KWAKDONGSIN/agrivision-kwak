# 구조 사이클 2 — 2차 보통 검수

검수 범위: 중단된 Claude 검수 산출물을 보존하고, 별도 사본 `../codex_resume/`에서 다른 경로로 검증했다. 실서버는 재시작하지 않았다.

## 판정
서버 분리의 API·저장 결과는 기준선과 동일하다. 서버 분리 검증은 통과하지만 구조 목표 전체 달성으로 표현하면 안 된다. 전체 배포 관문은 아직 실패이며 구조 5 이전 전환은 금지한다.

별도 API 시나리오는 네 과일의 두 번째 표본을 사용했다. flag→exclude→ok, 경계 밖/거꾸로/너무 작은 상자, 전부 탈락, 빈 목록, AI로 시작하는 이름, 잘못된 확정 종류, 되읽기를 검사했다. 첫 작업자의 계약검사·코드 생성 스크립트는 쓰지 않았다. 날짜·mtime 등 가변 필드만 명시적으로 정규화했으며 이름·메모·stem은 남겼다. API JSON 동일은 이 고정 입력 범위의 증거이지 모든 입력에 대한 수학적 증명은 아니다.

## 기존 검수의 실패를 어떻게 해석했나

- `stage2/logs/g1_mirror_gate.log`의 통합 4실패는 최종 산출물에 그대로 남은 실패가 아니다. 후속 `g3_merged_after_fix.log` 536/0과 이번 독립 사본 536/0으로 재확인했다.
- 기존 A/B `before_true` 대 `after_live`는 API·내보내기·라우트·status 차이 0, 상자 JSON 원시 지문 12개만 달랐다. 시각이 들어간 JSON이므로 원시 지문만으로 동일 판정을 내리지 않았다. 이번에는 별도 요청과 정규화 JSON으로 재검증했다.
- 더 오래된 `_archive/pre_refactor_260920`은 카운팅 5 마지막 수정 전 내용도 포함한다. 그것을 곧바로 최종 기준선 코드라고 부르지 않는다. API 별도 시험은 `stage2/code_before_true`를 사용했고, 고정 기준선도 별도로 대조했다.
- **전체 명령 종료코드는 1이다.** 단정 1,102/0과 명령 성공은 다르다. ⑤의 `r_page_index`, `r_page_box`, `r_static_app_js` 각 bytes/sha256, 합계 6칸이 다르다. 정적 파일 분리로 설명되지만 검수자가 임의로 기준선을 덮어쓰지는 않았다.

## 인수인계 요구 중 아직 미달인 것

1. 공개 최상위 함수 113개 중 반환 타입 표기는 0개, docstring은 91개다. «공개 함수 docstring+타입 힌트 완료»라고 쓰면 거짓이다. 중첩 함수까지 포함하면 157개/설명 누락 45개다. `evidence/architecture.json` 참조.
2. 80줄 초과 함수: export_boxes_to 92, api_save_instances 105, api_list 141. register는 라우트 등록 묶음이라 별도로 길다. 동작 보존을 우선해 이번 검수에서 본문을 재작성하지 않았다.
3. 상태 쓰기는 core/status_store.py로 모였지만, 외부 코드가 같은 파일에 임의로 쓰는 것까지 막는 저장소 계층은 아니다. 기존 다중 요청/여러 프로세스 한계가 사라진 것은 아니다.
4. 규칙표의 옛 코드 칸·일부 문장·배율 버그 주장은 구조 4에서 실제 코드 기준으로 정정해야 한다.
