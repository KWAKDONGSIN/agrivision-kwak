## 4. 🔴 교수님 숙제 ⑦ 답 — 크롭 방식 확인 결과

교수님이 마지막 10분을 여기에 쓰셨고, 카톡에도 답이 없던 숙제입니다.
**코드를 직접 열어서 확인했습니다.**

### 확인된 사실

| 질문 | 답 | 근거 (코드 위치) |
|---|---|---|
| 리사이즈인가 크롭인가? | 🔴 **크롭입니다. 리사이즈는 전혀 안 합니다** | `semseg/augmentations.py:257` `RandomCrop` |
| 비율 기준 크롭인가? | 🔴 **아닙니다. 화소 고정(512×512)입니다** | 같은 파일 `tH, tW = self.size` |
| 이미지가 크롭보다 작으면? | **0으로 패딩**합니다 (마스크는 ignore 라벨) | 같은 파일 265~270줄 |
| 검증·평가는? | 🔴 **`CenterCrop` 입니다** — 사진 **가운데 512×512만 채점** | `semseg/augmentations.py:409` `get_val_augmentation` |

### 왜 이게 문제인가 (교수님 지적이 정확했습니다)

CERTH 포도 원본은 **2160×3840** 입니다. 여기서 512×512를 자르면 긴 변의 **13%**,
화면 넓이의 **약 3%** 짜리 조각입니다. 저화소 데이터셋에서는 같은 512가 화면 대부분을
차지합니다. **같은 설정인데 담기는 내용이 완전히 달라집니다.**

더 심각한 건 **평가 쪽**입니다. `CenterCrop` 이므로 4K 원본을 그대로 쓰면
**사진 가운데 3%만 채점**하고 나머지는 아예 안 봅니다.

### 내가 적용한 해법

교수님 말씀 (56:31) — *"비율은 유지를 해가지고 ... **768×768** 정도가 가장 많이 쓰는 화소"*

- 포도 원본 비율은 2160:3840 = **1 : 1.778**
- 긴 변을 **1024** 로 리사이즈 → **576 × 1024**
- 576 × 1024 = **589,824 픽셀 = 768 × 768 과 정확히 같은 화소수**
- → **비율을 왜곡하지 않으면서** 교수님이 말씀하신 화소 예산을 정확히 맞춥니다
- 덤: 576도 1024도 512보다 크므로 **패딩이 전혀 안 생깁니다**
- 리사이즈는 **미리 한 번만** 수행 → 교수님이 지적하신 "매번 리사이즈해서 느린 문제"도 해결

적용 위치: `tools/prepare_certh_grape.py --resize 1024` (기본값)
