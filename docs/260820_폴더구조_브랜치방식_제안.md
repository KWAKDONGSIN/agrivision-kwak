## 0. 결론 먼저

**「자료는 폴더 브랜치, 코드는 git 브랜치」 두 겹으로 갑니다.**

| 무엇 | 브랜치 역할을 하는 것 | 반영(merge) 방법 |
|---|---|---|
| 문서·논문·그림·설정파일 | `work/<내이름>/` 폴더 | 다 되면 카톡 → 공용 폴더로 복사 + `변경기록.md` 한 줄 |
| 실험 코드 (`semantic-segmentation`) | **git 브랜치** `<내이름>/<작업>` | pull request 대신 카톡 → 곽동신이 `main` 에 merge |
| 데이터셋·체크포인트 | 브랜치 없음 (읽기 전용, 복사 금지) | — (`SAVE_DIR` 을 내 폴더로 바꿔 새로 만든다) |

이유 — 코드는 git 이 «누가 어디를 고쳤나» 를 줄 단위로 기록하고 충돌도 잡아 주지만,
PDF·데이터·수십 GB 산출물은 git 에 넣으면 안 됩니다. 그래서 둘을 다른 도구로 관리합니다.

## 2. 코드 — git 브랜치로 작업하는 법

공용 `main` 은 `/data/project/2026summer/kds0206/semantic-segmentation` (= `04_experiments/코드_레포`).
여기서 직접 고치지 않고 **내 폴더에 clone** 해서 브랜치를 땁니다.

```bash
# 처음 한 번 — 내 작업 폴더에 복제 (12MB, 데이터는 안 딸려옴)
cd /data/project/2026summer/platform/work/<내이름>
git clone /data/project/2026summer/kds0206/semantic-segmentation code
cd code
git checkout -b <내이름>/<무슨작업>        # 예: ahn/sliding-window-eval

# ... 클로드와 작업 ...
git add -A && git commit -m "슬라이딩 윈도우 평가 추가"

# 반영하고 싶을 때 — 카톡에 "브랜치 ahn/sliding-window-eval 반영 부탁" 한 줄
# 곽동신이 공용 main 에서:
#   git fetch /data/project/2026summer/platform/work/<내이름>/code <브랜치>
#   git merge FETCH_HEAD
```

- clone 안의 `configs/*.yaml` 경로는 전부 절대경로라 **clone 에서도 그대로 학습이 됩니다.**
  단 `SAVE_DIR` 은 상대경로(`output/...`)이므로 clone 폴더 안에 결과가 생깁니다 — 원본 `output/` 을 건드리지 않아 안전합니다.
- 공용 `main` 의 미커밋 변경은 2026-08-20 정리 커밋(`0057df6`) 했습니다. `work/<이름>/code` 는 그 시점의 clone 입니다.
